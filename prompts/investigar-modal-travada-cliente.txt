INVESTIGAÇÃO — MODAL ABRE SÓ O BACKDROP E A TELA TRAVA (CLIENTE ESPECÍFICO, SEM ERRO NO CONSOLE)

SINTOMA
- Ao abrir uma modal, aparece o fundo escuro (backdrop), a modal não aparece e a tela fica travada.
- Console do navegador SEM erros.
- Acontece com UM cliente/escritório específico (com outros, a mesma modal abre normal). O usuário vai informar no chat qual tela/modal e o identificador do cliente (não registrar esse identificador em arquivos versionados).

CONTEXTO CONFIRMADO PELO USUÁRIO
- Tela: Clientes → painel "Visão 360°" do cliente → botão "Editar" (cabeçalho roxo). Ao clicar, aparece o backdrop e tudo trava. Só com ESTE cliente; os outros abrem normal.
- O painel desse cliente mostra: subtítulo "Sem informação", "Score de cadastro 22%" e "7 campos pendentes" — ou seja, um cadastro com MUITOS campos vazios/nulos.
- Histórico relevante: houve um incidente anterior em que clientes perderam endereços e o tipo de pessoa passou a aparecer sempre como "Jurídica" (gravação do documento inteiro em vez de $set). Este cliente pode ter dados corrompidos/ausentes por causa disso.

HIPÓTESE PRINCIPAL (verificar primeiro)
- O formulário de edição do cliente quebra ou entra em laço ao receber campos nulos/ausentes/inconsistentes deste cadastro, por exemplo:
  - tipo de pessoa nulo/inválido ou incoerente com o documento (CPF x CNPJ) — o form troca de validadores/máscara em loop (valueChanges que altera o próprio campo, setValidators + updateValueAndValidity disparando de novo);
  - máscara de CPF/CNPJ/telefone/CEP recebendo null, objeto ou texto fora do formato e entrando em laço;
  - endereço nulo (ou lista de endereços nula em vez de vazia) e o form tentando montar FormArray/FormGroup a partir de null;
  - campos de select/autocomplete (UF, cidade, estado civil, profissão etc.) com valor que não existe na lista, disparando busca infinita, ou carregando uma lista enorme (ex.: todas as cidades) sem paginação;
  - patchValue/setValue com estrutura diferente do form (lança erro dentro de um subscribe que tem catchError silencioso, e a modal nunca termina de abrir).
- Comparar o JSON do GET deste cliente com o de um cliente que abre normal: campos nulos, ausentes, tipos diferentes (string x número x objeto), listas nulas.

OUTRAS HIPÓTESES (se a principal não se confirmar)
1. Dado específico desse cliente que quebra a modal SEM erro visível:
   - erro engolido: subscribe/pipe com catchError que retorna EMPTY/of(null), try/catch sem log, .catch vazio, ErrorHandler customizado que não loga, interceptor HTTP que trata o erro e não propaga — a modal fica esperando dado que nunca chega (ex.: só renderiza com *ngIf="dados" ou com @if e o dado nunca vem);
   - campo nulo/ausente/formato inesperado nos dados desse cliente (data inválida, enum desconhecido, lista nula em vez de vazia, caracteres especiais, texto enorme), quebrando um pipe/getter ou um switch sem default;
   - permissão/escopo: para esse usuário a chamada volta 401/403/204/vazio e o front não trata (fica esperando).
2. Volume: o cliente tem MUITOS registros (ex.: milhares de itens num select/lista da modal) e o navegador trava renderizando ou calculando (thread principal ocupada — por isso “nada no console”).
   - verificar se a página responde a scroll/hover; se não responde, é thread travada.
   - procurar laços pesados, filtros/ordenações em getters chamados a cada ciclo de detecção, *ngFor sem trackBy em listas grandes, regex custosa, select sem virtualização/paginação.
3. Loop de detecção de mudança/infinito: getter ou pipe impuro que muda estado a cada ciclo, subscribe que reabre a modal, show() chamado repetidamente (vários backdrops empilhados: contar elementos .modal-backdrop no DOM).
4. Modal renderizada atrás do backdrop (z-index/stacking context) só para esse cliente: ex.: conteúdo que injeta CSS/HTML (campo rico, HTML do cliente) quebrando o layout.

COMO INVESTIGAR
- Reproduzir com o usuário/cliente informado (pela interface; NÃO alterar dados no banco; leitura do banco só se o usuário autorizar e para comparar dados).
- No navegador: aba Network (todas as chamadas ao abrir a modal: status, tempo, tamanho da resposta, resposta vazia/erro), aba Performance (gravar o clique e ver se a thread principal fica presa e em qual função), Elements (existe .modal? display/opacity/z-index? quantos .modal-backdrop?).
- No código: ler o fluxo da modal (quem abre, initialState, ngOnInit, serviços chamados, tratamento de erro, condições de exibição do conteúdo).
- Comparar a resposta da API desse cliente com a de um cliente que funciona (estrutura e tamanho).
- Ativar log temporário onde houver catchError/try-catch silencioso para expor o erro (remover depois).

ENTREGA (antes de corrigir)
- Causa-raiz com evidência (qual chamada/dado/função, print ou trecho da resposta sem dados pessoais).
- Por que não apareceu erro no console.
- Proposta de correção (front e/ou back) e o que muda para os outros clientes.
- Só implementar a correção depois da minha confirmação, a menos que seja um ajuste óbvio e localizado (ex.: tratar nulo, exibir erro em vez de engolir); nesse caso, explique.
- Se a causa for dado corrompido: corrigir o FRONT para abrir a edição mesmo com campos nulos/incoerentes (valores padrão seguros, sem laço) e mostrar o que está faltando; NÃO corrigir o dado no banco (o banco é do usuário) — entregar a lista exata dos campos problemáticos deste cliente para ele corrigir.
- Bônus: listar outros pontos do sistema com o mesmo padrão de erro engolido (catchError → EMPTY sem log/aviso), para eu decidir se corrigimos depois.

Sem testes automatizados, sem lint, sem scripts de validação.
