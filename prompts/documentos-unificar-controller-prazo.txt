DOCUMENTOS — MOVER OS ENDPOINTS DE DOCUMENTOS DE PRAZO PARA A CONTROLLER DA CLOUD

PROBLEMA
Foi criada uma controller SEPARADA só para os documentos de prazo (listar, enviar e baixar anexos de um prazo). Isso está errado: TODO o fluxo de documentos fica na controller principal da Cloud (a mesma que já atende o explorador de Documentos, organizada em arquivos parciais). Já é a 2ª/3ª vez que isso acontece.

REGRA PERMANENTE (vale para este e para os próximos prompts)
- NÃO criar controller nova para nada de Documentos/Cloud. Todo endpoint novo de documentos entra na controller da Cloud que já existe (pode usar um arquivo parcial dela, seguindo o padrão já usado no projeto).
- Antes de criar qualquer controller, service ou repository novo, procure o equivalente existente e reutilize.
- Registrar essa regra no AGENTS.md do back (seção de convenções), se ainda não estiver lá.

O QUE FAZER
1. Investigar:
   - localizar a controller separada de documentos de prazo e listar os endpoints, verbos, rotas, parâmetros, validações de permissão e o Business/serviço que cada um chama;
   - procurar outras controllers criadas para Documentos/Cloud nas últimas alterações (ex.: processamento de documentos, classificações). Liste-as na entrega. Mova só a de prazo agora; as outras eu decido depois.
2. Mover os endpoints de prazo para a controller da Cloud (num arquivo parcial, se o projeto já usa esse padrão):
   - mesmos comportamentos, mesmas validações de permissão (Documentos › Visualizar para ler/baixar; Documentos › Remover para enviar; mais Prazos › ExibirLista, conforme o permissionamento já feito) e mesmo Business. Só muda o lugar;
   - rotas: seguir o padrão de rotas da controller da Cloud (ex.: sob o prefixo da Cloud/explorador), com nomes coerentes com os outros endpoints de lá.
3. Apagar a controller separada e qualquer registro dela (DI, atributos, docs, Swagger), sem deixar código morto.
4. Front: localizar onde o front chama esses endpoints (serviço de documentos de prazo, explorador, tela de prazo) e trocar para as rotas novas. Conferir também se outras telas do sistema (fora de Documentos, ex.: a tela do prazo/processo) usam as rotas antigas e ajustar todas.
5. Atualizar a documentação de regras de negócio de documentos de prazo com as rotas novas.

RESTRIÇÕES
- Não mudar regra de negócio, contrato de resposta nem permissões, só o local e as rotas.
- Não mexer em outros fluxos.
- Sem testes, sem lint, sem scripts de validação.

ENTREGA
- Endpoints antes → depois (verbo + rota), arquivos alterados (trechos relevantes) e lista dos pontos do front ajustados.
- Lista de outras controllers de Documentos/Cloud encontradas (item 1).
- Seção "Explicações" e pendências.

ESTILO DE CÓDIGO (perfil do Jeziel — obrigatório)
- Nomes mistos: domínio em português (ObterCliente, valorTotal), termos técnicos em inglês (Repository, GetById).
- Comentário-resumo em português no topo de cada método.
- Retorno antecipado; if de uma linha sem chaves; nulos com if explícito; ternário só simples; switch clássico; var.
- LINQ básico encadeado (um operador por linha). Avançado só com comentário explicando.
- Back: seguir Controller → Business → Repository; sem genéricos/extension methods novos; Model→DTO manual; erro de negócio com objeto de resultado; Mongo com $set só dos campos alterados.
- Front: subscribe simples atribuindo em variáveis (+ takeUntilDestroyed); RxJS além de map/filter/tap só com explicação; template só exibe e condições simples.
- Valores fixos direto no código (constante só se repetir ou for regra configurável).
- Clean code/boas práticas: aplique, mas EXPLIQUE antes (na mini-spec) e na entrega.
- Todo trecho avançado: comentário curto em português no código + seção "Explicações" na entrega (o que faz, por que, versão simples equivalente, como debugar).
- Prefira variáveis intermediárias nomeadas (bom para breakpoint) a expressões longas.
