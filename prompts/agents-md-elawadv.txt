## 3.1 Cores — Modo claro e escuro
Toda alteração que envolva cor (texto, fundo, borda, ícone, sombra, hover, focus,
disabled, gráficos, badges, estados) DEVE funcionar nos modos claro e escuro.
- Nunca use cor hardcoded (#hex, rgb(), nomes de cor) em componente ou tela.
  Use sempre os tokens/variáveis de tema do UIKit.
- Se o token necessário não existir, crie-o no arquivo de tema com valor para
  AMBOS os modos. Nunca defina só um lado.
- Ao alterar um token existente, revise o valor correspondente no outro modo.
- Garanta contraste legível nos dois modos (texto x fundo, ícone x fundo).
- Estados (hover, focus, active, disabled, selecionado) também precisam de valor nos dois modos.
- Imagens/SVGs com cor fixa: use `currentColor` ou token de tema.
- A conferência dos dois modos é feita lendo o código e os tokens.
  NÃO abra navegador para isso sem pedido explícito (seção 8).
- Se encontrar cor hardcoded no trecho que você está alterando, substitua por
  token. Fora do trecho, apenas aponte; não refatore sem pedido.
- Na resposta, informe em uma linha: `Tema: tokens usados/criados → <lista>`.

## 3.2 Verificação estática obrigatória (sem testes, sem lint, sem navegador)
"Implementado" só pode ser declarado após esta verificação passar.

### Ciclo de autocorreção
1. Antes de implementar: leia os arquivos que serão afetados e os que os
   importam/consomem. Identifique o que pode quebrar.
2. Implemente.
3. Rode a verificação da área alterada (NUNCA lint, ver seção 4):
   - Front (Angular): `npx tsc --noEmit -p tsconfig.app.json`, depois
     `npx ng build --configuration development`.
   - Back (.NET): `dotnet build` na solution.
   - Ambos, se a alteração for multidisciplinar.
4. Se houver erro ou warning novo causado pela alteração:
   corrija a causa-raiz e volte ao passo 3.
5. Máximo de 3 ciclos. Se persistir, PARE: mostre o erro exato, a hipótese
   de causa e NÃO declare como concluído.

### Revisão de runtime (o que o build não pega)
Após o build passar, revise no código, sem executar:
- Front: componente/standalone com todos os imports; serviços injetados
  existem e têm provider; rotas e lazy-loads apontam para caminhos válidos;
  acesso a dados possivelmente nulos protegido (`?.`, `@if`); subscriptions
  com unsubscribe/takeUntilDestroyed; nomes de campos batem com o contrato da API.
- Back: serviço registrado na DI; rota/verbo/DTO coerentes com o front;
  campos novos no Mongo tratam documentos antigos sem o campo; null checks.
- Busque usos de tudo que foi renomeado, movido ou removido (grep no projeto)
  e ajuste todos.

### Problemas detectados durante a implementação
- Se perceber que algo VAI quebrar (efeito colateral, contrato divergente,
  dependência ausente), resolva dentro do mesmo ciclo, antes de entregar.
- Se a correção exigir mudar algo fora do escopo pedido ou decidir regra de
  negócio, NÃO decida sozinho: pare e pergunte.

### Declaração final obrigatória
Toda resposta com código termina com:
`Verificação: tsc ✅/❌ | build ✅/❌ | ciclos: N`
Proibido escrever "concluído", "feito" ou equivalente sem essa linha com tudo ✅.
