A1. [P1] USUÁRIO ADICIONAL NÃO ENTRA COMO PARTICIPANTE (ConversaBusiness.cs ~1462)
Problema: a criação da conversa direta passa a lista de usuários adicionais vazia, e CriarParticipantes só adiciona o remetente automaticamente quando ele é advogado titular. Conversa iniciada por um ADICIONAL fica sem ele como participante, e o envio falha na validação.
Correção:
- Na criação da conversa direta, os participantes são EXATAMENTE: o usuário logado (titular OU adicional, com o tipo de participante correto) + o cliente.
- Não mexa no comportamento de CriarParticipantes para os outros fluxos. Se precisar, crie um caminho explícito para a conversa direta (ex.: um método privado que monta os 2 participantes) em vez de mudar a regra geral.
- Confirme que a chaveDireta usa o id do usuário logado (titular ou adicional), conforme a regra titular × adicional do prompt original.
- Confirme que o adicional é colocado no grupo SignalR conversa-participante:{id} com o MESMO id gravado como participante.

A2. [P1] ÍNDICE ÚNICO DE chaveDireta COM NULOS (ConversaRepository.cs ~16, ConversaModel.cs ~68)
Problema: o índice é unique + sparse, mas o modelo grava `chaveDireta: null` nas conversas dos outros fluxos. O sparse NÃO ignora campo existente com valor null, então duas conversas com null colidem (DuplicateKey) e quebram os outros fluxos de criação.
Correção:
- No ConversaModel: [BsonIgnoreIfNull] em ChaveDireta (o campo não é gravado quando nulo).
- Trocar o índice para UNIQUE com partialFilterExpression: { chaveDireta: { $type: "string" } } (no driver: CreateIndexOptions<ConversaModel> { Unique = true, PartialFilterExpression = Builders<ConversaModel>.Filter.Type(x => x.ChaveDireta, BsonType.String) }). Remova o Sparse.
- Se o índice antigo já tiver sido criado em algum ambiente com o mesmo nome e opções diferentes, a criação vai falhar: use um NOME NOVO de índice (ex.: ux_conversas_chaveDireta_v2) e, na inicialização, remova o índice antigo se existir (pelo nome antigo), no mesmo mecanismo que cria os índices.
- Entregue também (sem executar) o comando do mongo shell para limpar documentos que já tenham sido gravados com chaveDireta: null:
  db.conversas.updateMany({ chaveDireta: null }, { $unset: { chaveDireta: "" } })

A3. [P1] BADGE DA SIDEBAR CONDICIONADO AO ESTADO ERRADO (sidebar.component.html ~68)
Problema: os dois pontos do template usam `MenuAberto`; o pedido é esconder quando a sidebar está REDUZIDA (`isReduzido`). Em telas pequenas ou no menu sobreposto, MenuAberto e isReduzido não são inversos, e o badge some ou aparece na hora errada.
Correção: nos DOIS pontos, mostrar o badge só quando `!isReduzido` (e total > 0). Não use MenuAberto para isso.

A4. [P2] LEITURA EM LOTE DO PORTAL MARCA NOTAS INTERNAS (ConversaBusiness.cs ~1356, ConversaRepository.cs ~440, ConversaModel.cs ~15)
Problema: a rota do portal passa somentePublica=true, mas a consulta das mensagens a marcar ignora esse parâmetro (só exclui eventos de sistema). Assim, NotaInterna também é marcada como lida pelo cliente.
Correção: quando somentePublica=true, a consulta considera SOMENTE mensagens públicas (exclui NotaInterna E eventos de sistema). Aplique o MESMO filtro na contagem de não lidas do cliente, se ela usar outra consulta (o cliente nunca pode ter contador de nota interna). Confira também a rota interna: o titular/adicional pode marcar públicas e internas (comportamento atual).

A5. [P2] DEBOUNCE PODE MARCAR COMO LIDA COM A ABA OCULTA (conversas.component.ts ~1268)
Problema: o callback de 300ms chama o POST /lida sem revalidar as condições.
Correção: DENTRO do callback, antes de chamar, revalidar: document.visibilityState === 'visible' E a conversa ainda é a aberta (mesmo conversaId) E o drawer ainda está aberto. Se alguma falhar, não chama (e não zera o contador local). Aplique o mesmo no componente equivalente do PORTAL.

A6. [P2] `leituraAtualizada` SÓ PARA QUEM LEU (ConversaRealtimeNotifier.cs ~43)
O modelo tem leituras por mensagem (leiturasMensagens), então o "visto por" se aplica:
- Continue emitindo `leituraAtualizada` { conversaId, tipoEvento: 'lida' } para o grupo do PRÓPRIO participante (sincroniza as abas dele).
- Emita também para os DEMAIS participantes da conversa: `leituraAtualizada` { conversaId, participanteId (quem leu), lidaAte (data/id da última mensagem lida), tipoEvento: 'vista' }.
- REGRA: leitura feita pelo titular/adicional de uma NOTA INTERNA nunca é emitida ao cliente. Ao cliente só vai leitura de mensagens públicas.
- Front: ao receber tipoEvento 'vista', apenas atualizar o indicador de "visto/lido" da mensagem, se a tela já exibir esse indicador. Se não exibir, não criar UI nova agora: só não quebrar (não recalcular contador do usuário com esse evento).
